# LuaTools macOS acceptance ledger

The current Windows implementation uses LuaLoader (`winmm.dll`, LTSP), with the desktop `CefInjectorService` and a Millennium-compatible JavaScript polyfill. The macOS target must follow LuaLoader as the primary loader, not require Millennium. The desktop CDP bridge now owns LuaTools RPC even when Millennium is present. Its `window.Millennium` compatibility wrapper passes unrelated plugins through unchanged. Native LuaLoader bootstrap/activation remains to be implemented and tested in Steam.

This checkout is not yet the requested full release. Its native SwiftUI surface remains incomplete. Track full requirements together with `BetterSteamTools/macos/IMPLEMENTATION_STATUS.md`.

Verified: atomic Lua replacement (including same source/destination), explicit remove errors, strict HTTP framing and methods, malformed AppID rejection, bounded fragmented TCP requests, a real loopback listener, origin rejection, and explicit errors for unknown/unimplemented RPC routes. `LuaToolsMacSelfTest` runs those cases without changing a real Steam installation.

The CDP transport now keeps a single correlated response reader per socket and waits for actual evaluation results. `LuaToolsCDPSelfTest` runs against a real loopback WebSocket fixture (fragmented/out-of-order replies, notifications, cancellation, timeout, disconnect, validated discovery targets, default-context and nonce isolation, navigation, LuaLoader selection, rejection of a legacy-loader handshake, failed frontend acknowledgement and reconnect). `Tests/CDP/bridge.test.cjs` executes the bridge in separate JavaScript realms and verifies response IDs, stale replies, error propagation, pending promise disposal, LuaLoader priority, preservation of other Millennium plugins, exact restoration of the original API on disposal and pending requests surviving late Millennium activation. The bridge does not set the frontend's UI-ready flag. These tests establish transport behavior, not Chromium/Steam end-to-end acceptance.

The default inspector authorizer now uses libproc to enumerate TCP listener owners and their executable paths before discovery and again before opening returned WebSocket targets. It accepts only loopback listeners owned by native helper executables inside the selected Steam bundles. Tests inspect a real loopback test listener and reject foreign/Wine owners, wildcard listeners, another installation and a helper symlink escaping the approved app. A read-only diagnostic against the host's occupied port 8080 identified Windows Steam/CrossOver owners and refused native authorization. This prevents confusing the running Windows client with the native macOS acceptance target; it does not prove native Steam activation. WebSocket fixtures explicitly inject a test authorizer instead of weakening the production default.

The native Steam 1792618285 arm64 binaries contain a `-cef-enable-debugging` command-line option, a `-devtools-port` value, loopback-address construction and a Steam UI debug marker. The exact-build evidence is recorded in `analysis/1792618285-inspector.json`. LuaTools can explicitly launch a closed Steam with those arguments, reuse an authorized running inspector, and report when Steam needs to be restarted; it refuses a foreign listener. Tests verify the process arguments and these decisions without restarting the user's Steam. Whether the marker enables the native startup path, automatic LuaLoader startup, and live in-client plugin behavior remain unproved.

`LuaToolsDaemon` and the graphical app now share one background service implementation for the local API and LuaLoader CDP transport. The service retries when the plugin or Steam inspector is unavailable; when assets change it reports that the existing page needs navigation or reload, then uses the new version without injecting twice. The app reuses a loopback service only when the listener belongs to its own app bundle. The LaunchAgent installer starts the bundled daemon, restores its previous plist on bootstrap failure, and refuses foreign plist files. Tests use a real WebSocket fixture for service startup and asset changes across navigation, plus simulated `launchctl` results for agent install, update, rollback and removal. A development ZIP now bundles both executables, the plugin and the bridge resource; its extracted app is checked for an ad-hoc signature and the daemon verifies its resources. This ZIP is not notarized and does not include an approved BetterSteamTools payload. Real launchd activation, automatic Steam inspector enablement and live Steam acceptance remain outstanding.

The plugin installer validates bounded ZIP content and compatibility metadata, stages updates and keeps a previous version. A synced journal, process lock and atomic directory swaps support recovery for installation, rollback and removal. Tests terminate child processes at each mutation checkpoint, check rollback and reject conflicting external edits and unmanaged directories. A known SHA-256 can be supplied, but no authenticated release channel has been established yet.

The games page now reads numeric installed Lua files from Steam's `stplug-in` directory and recognizes the Windows header-name convention. It refreshes after manual Lua or ZIP installation. Tests cover missing folders, unrelated files, disabled files and symlinks. Steam name lookup, artwork, filtering, editing, builds and live synchronization still require implementation.

The macOS account service implements the Windows client's Discord bot-code redemption, Supabase magic-link verification and access-token refresh. Sessions are stored in the macOS Keychain; the settings view can sign in and out. A locked compare-and-swap and a sign-out tombstone stop a stale refresh from restoring a cleared session. A cancellable process lock serializes token rotation; after acquiring it, a waiting instance reuses a fresh session or refuses a changed account. In-memory credential and HTTP fixtures test the request contract, persistence, single-flight refresh, concurrent service instances and sign-out racing with a refresh. Separate child-process tests verify the actual lock's exclusion, cancellation, abrupt-exit release and symlink rejection without using Keychain. No real credentials or Keychain prompt are used by these tests. Browser OAuth and an actual sign-in/Keychain integration test remain outstanding.

The plugin's headless add path can query the original dynamic source endpoint, select an available standard source, download through the authenticated lua.tools endpoint and install either bare Lua or a ZIP with manifests. HTTP and CDP dispatch share the same coordinator; cancellation stops a pending download and installation is committed transactionally. Fixtures exercise the actual routing and installation logic without a real account. The original source availability service uses HTTP; the app's ATS exceptions are limited to that upstream IP and localhost, while credentials go only to lua.tools over HTTPS and redirects are rejected. A real public AppID 480 lookup returned two entries from both the standalone daemon and the extracted app after adding the ATS exception. A real authenticated download, Steam UI interaction, Hubcap/keyed sources, download progress, FastFetch and full Windows parity remain unverified or unimplemented.

Both the native CDP composer and Millennium Lua backend embed the plugin's base CSS, theme metadata and theme styles in the delivered frontend; relative theme URLs no longer need to resolve on the Steam store origin. The self-tests compose the real packaged assets, reject directory traversal in theme names and verify the mocked Lua composer. Settings/database/fixes methods now forward real backend results instead of returning empty successful placeholders.

Lua package installation reads ZIP local and central records in bounded memory instead of extracting archive paths to disk. It rejects traversal, symlinks, overlapping records, duplicate paths, encrypted entries and CRC errors, and enforces expanded-size limits. Raw and ZIP-wrapped Steam manifests are parsed for depot ID, GID, encrypted filenames and installed size; their declared identity must match the destination filename, while original bytes are preserved. `LuaToolsMacSelfTest` exercises actual stored/deflated ZIPs, ZIP64 end/entry records, wrappers, metadata mismatch, path traversal, symlinks, CRC corruption and preservation of an existing Lua after failed installation. Multi-volume archives are rejected. The SwiftUI shell has macOS navigation for Resumen, Juegos, Lua y depots, Operaciones and Ajustes, with file pickers for `.lua` and ZIP packages.

Standalone manifests can also be selected in the app and installed as one transaction. Tests verify byte preservation, source-equals-destination, rejection of mismatched metadata and symlinks, and preservation of earlier files if validation fails. Live Steam depot use remains unverified.

Lua and depot writes now share a per-Steam-directory file lock and a synced journal with backups. Startup and subsequent install/remove operations recover prepared transactions; a committed transaction is retained. Child-process tests terminate at eight checkpoints, including before renames, between three file writes and after commit, and verify bytes, permissions and temporary-file cleanup. Tests verify that an external edit causes a recovery conflict instead of being overwritten and that a second process waits for the first process's transaction lock. These tests simulate process termination, not a machine power loss; live Steam interaction remains to be tested.

Removing a Lua now uses that same process lock and journal for both the active and disabled files. Tests cover interruptions at each removal step, idempotence and external replacement conflicts. The CDP bridge rejects HTTP failures so that a plugin action cannot report success merely because the backend returned an error response.

The UI no longer edits Steam Info.plist through a second unsafe implementation: activation delegates to the packaged BetterSteamTools CLI and requires a signed manifest. The packaged helper and approved hook payload still need release packaging.

Still required: complete desktop UI and service parity; downloads and source selection; builds/fixes/manifests and settings; verified dependency/install/update/rollback lifecycle; plugin artifact authentication; native LuaLoader bootstrap/activation and live CDP/frontend behavior; process/menu-bar/LaunchAgent integration; signed app/DMG generation; and all live Steam/game acceptance tests. Pure Lua tests cover separate Steam data/client paths, safe POSIX quoting, backend service identity, invalid AppIDs, capabilities, asset composition and forwarding every frontend RPC name. These use mocked Millennium modules; the plugin assets have not been proven to work against a live macOS Millennium runtime.
